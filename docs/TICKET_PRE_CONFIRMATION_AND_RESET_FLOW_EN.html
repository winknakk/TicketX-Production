🚀 Two-Step Ticket Confirmation & Reset Flow Architecture

Pre-Ticket Verification, Context Modification & Cancellation System (TicketX / AutomationX)

System Architecture & Flow Prompt Engineering Specification | Date: August 31, 2026

Architecture & Engineering Specification

1. Background & Problem Statement

❌ Legacy System (Immediate Ticket Creation)
  • Instant creation on first turn: Bot immediately invoked create_ticket upon receiving the first customer report.
  • Junk / Orphaned Tickets: Typos, wrong module selections, or customer self-resolutions produced invalid tickets on Plane.so.
  • No Review / Reset Mechanism: Customers had no opportunity to review, correct, or cancel before developer assignment.
🎯 New Architecture (Two-Step Confirmation)
  • Intake & Summarize First: Extracts module, symptom, and severity, presenting a concise summary for confirmation.
  • Confirmed-only Creation: Tickets (TCK-2026-xxxxx) are created in PostgreSQL and Plane.so only after explicit customer consent.
  • Full Support for Edit & Reset: Allows customers to modify details or abort seamlessly without leaving DB clutter.

2. Core Execution Flow

1
Customer Incident Intake: Customer sends an issue description in LINE (e.g. "Reporting an issue: Loan Repayment System. Need to revert status from Paid to Pending Payment.")
2
AI Gatekeeper Analysis: E.D.I.T.H. extracts entities and flags the action as CONFIRM_REQUIRED (No database insertion performed).
3
Summary & Confirmation Prompt: Bot replies in LINE with a structured summary asking the customer to confirm.
4
Customer Decision Handling:
  • ✅ Customer Confirms ("Confirm / Yes"): Executes Sub Flow ➔ Creates TCK-2026-90928 ➔ Syncs to Plane.so ➔ Returns Ticket ID & SLA.
  • 📝 Customer Modifies ("Change to..."): Bot updates the issue summary and re-confirms.
  • ❌ Customer Cancels ("Cancel / Fixed already"): Bot aborts the ticket creation and acknowledges politely with zero DB pollution.

5. Gatekeeper Prompt Configuration (E.D.I.T.H.)

# TWO-STEP TICKET CONFIRMATION & RESET RULES

1. NEW INCIDENT INTAKE:
   - When customer reports a new bug/outage/issue AND no pending confirmation in history:
   - Output ticket_action: "CONFIRM_REQUIRED"
   - Extract subject, summary, priority, severity
   - The system will summarize and ask the customer to confirm before creating the ticket.

2. CUSTOMER CONFIRMATION:
   - When previous message asked for confirmation AND customer confirms ("Confirm", "Correct", "Yes", "OK", "Proceed"):
   - Output ticket_action: "CREATE"
   - Output targetAgent: "support"
   - Pass accumulated subject and summary to create the ticket.

3. CUSTOMER CORRECTION:
   - When customer modifies details ("No, it is...", "Change to..."):
   - Output ticket_action: "CONFIRM_REQUIRED" with updated summary.

4. CUSTOMER CANCELLATION / RESET:
   - When customer says "Cancel", "Nevermind", "Resolved", "Reset":
   - Output ticket_action: "NONE"
   - Output intent: "CANCEL_RESET"
   - Set reply_text to a polite cancellation acknowledgement.

6. Key Business Value

  • 🛡️ Zero Junk Tickets: 100% prevention of accidental, unverified, or misdirected ticket creation.
  • 🎯 High Data Accuracy: Pre-validated subsystem names and symptoms save engineering triage time.
  • 🤝 Human-Centric UX: Reassuring, conversational verification that builds user satisfaction.
  • ⚡ Clean Plane.so Board: Developer sprint boards remain clean and free from canceled tickets.
